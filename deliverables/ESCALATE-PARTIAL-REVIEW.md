## g013 — subqueryload with a string attribute name AttributeError on 2.0

````
Based on the provided sources, the SQLAlchemy 2.0 migration guide states that **string forms for loader options are removed in 2.0**. Source [3] explicitly covers this for "query options like :func:`_orm.joinedload`" and says "The string forms will all be removed in 2.0". While the examples in [3] show `joinedload`, the text refers to "query options like joinedload" broadly, which includes `subqueryload` (also a loader option).

The correct 2.0-compatible pattern is to use the mapped attribute directly:

```python

stmt = select(User).options(subqueryload(User.addresses))
```

The sources do not specifically mention an `AttributeError` for `subqueryload` with a string; they state the string forms are removed. If you are seeing an `AttributeError`, it may be because the string form is no longer recognized and the internal lookup fails, but the documentation only confirms the removal of string forms, not the exact exception type.
````

````
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

This refers to patterns such as that of :meth:`_query.Query.join` as well as
````

## g021 — should I still use relationship(..., backref=...) or is back_populates required now

**Verified answer chunks:** c02179  
**Pages given to the model:** c02179, c02180, c00605, c02618, c01328  
**Judge's reason:** Passage [1] states that `backref` is legacy and `back_populates` is preferred, but it does not say that `backref` remains available.

**Answer:**

````
Based on the SQLAlchemy 2.0 documentation, **`backref` is considered legacy and `back_populates` with explicit `relationship()` constructs is now preferred**, though `backref` remains available.

**From SQLAlchemy 2.0.51 [1]:**
> The `:paramref:`_orm.relationship.backref` keyword should be considered legacy, and use of `:paramref:`_orm.relationship.back_populates` with explicit `:func:`_orm.relationship` constructs should be preferred.

**Advantages of `back_populates` [1]:**
- Both ORM mapped classes include their attributes up front during class construction (not as a deferred step)
- Configuration is more straightforward with all arguments explicit
- PEP 484 typing features in SQLAlchemy 2.0 work better with explicitly declared attributes

**Equivalent pattern [2]:**
```python
# Legacy backref (still works but discouraged)
class User(Base):
    addresses = relationship("Address", backref="user")

# Preferred back_populates (explicit on both sides)
class User(Base):
    addresses = relationship("Address", back_populates="user")

class Address(Base):
    user = relationship("User", back_populates="addresses")
```

**Note on SQLAlchemy 1.4 [3,5]:** In 1.4, `backref` was not deprecated — the 1.4 tutorial [5] states "The `:paramref:`_orm.relationship.backref` parameter hasn't gone anywhere and will always remain available!" The shift to "legacy" status is specific to 2.0.

**Bottom line:** For new code in SQLAlchemy 2.0, use `back_populates` with explicit relationships on both sides. `backref` still works but is discouraged for the reasons above.
````

## g044 — autoload=True on Table without autoload_with what is the 2.0 way

**Verified answer chunks:** c01567, c01568  
**Pages given to the model:** c01562, c01568, c01563, c00952, c01552  
**Judge's reason:** Passage [2] states that explicit use of an Engine or Connection is required for reflection, but it does not mention that bound metadata has been removed.

**Answer:**

````
Based on the provided sources, the SQLAlchemy 2.0 way to reflect a table is to use **`autoload_with`** with an explicit `Engine` or `Connection` — the old pattern of using `autoload=True` on a `Table` with a bound `MetaData` (i.e., without `autoload_with`) is no longer supported because **"bound metadata" has been removed** [2].

Source [2] states:
> For schema level patterns, explicit use of an :class:`_engine.Engine` or :class:`_engine.Connection` is required.   The :class:`_engine.Engine` may still be used directly as the source of connectivity for a :meth:`_schema.MetaData.create_all` operation or autoload operation.

And it shows the new pattern:
```python
# engine level:
t = Table("t", metadata_obj, autoload_with=engine)

# connection level:
with engine.connect() as connection:
    t = Table("t", metadata_obj, autoload_with=connection)
```

The section title explicitly notes: **"Implicit" and "Connectionless" execution, "bound metadata" removed** [2]. Therefore, you must pass `autoload_with=engine` or `autoload_with=connection`; you cannot rely on `MetaData.bind` and `autoload=True` alone.
````

````
Library-level (but not driver level) "Autocommit" removed from both Core and ORM
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

In SQLAlchemy 1.x, the following statements will automatically commit
the underlying DBAPI transaction, but in SQLAlchemy
2.0 this will not occur::

    conn = engine.connect()

    # won't autocommit in 2.0
    conn.execute(some_table.insert().values(foo="bar"))

Nor will this autocommit::

    conn = engine.connect()

    # won't autocommit in 2.0
    conn.execute(text("INSERT INTO table (foo) VALUES ('bar')"))

The common workaround for custom DML that requires commit, the "autocommit"
execution option, will be removed::


    conn = engine.connect()

    # won't autocommit in 2.0
    conn.execute(text("EXEC my_procedural_thing()").execution_options(autocommit=True))

The method that is cross-compatible with :term:`1.x style` and :term:`2.0
style` execution is to make use of the :meth:`_engine.Connection.begin` method,
or the :meth:`_engine.Engine.begin` context manager::

    with engine.begin() as conn:
        conn.execute(some_table.insert().values(foo="bar"))
        conn.execute(some_other_table.insert().values(bat="hoho"))

    with engine.connect() as conn:
        with conn.begin():
            conn.execute(some_table.insert().values(foo="bar"))
            conn.execute(some_other_table.insert().values(bat="hoho"))

    with engine.begin() as conn:
        conn.execute(text("EXEC my_procedural_thing()"))
````

````
SQLAlchemy's first releases were at odds with the spirit of the Python DBAPI

to relational databases and ACID transactions in general.   SQLAlchemy 2.0 will
do away with all attempts to implicitly commit transactions, and usage patterns
````

## g049 — case statement WHEN list constructor deprecated positional form

**Verified answer chunks:** c01577, c01578  
**Pages given to the model:** c01577, c01578, c02278, c02687, c02025  
**Judge's reason:** Passages [1] and [2] show the positional form and deprecation warning, but do not state that the list form is removed in 2.0.

**Answer:**

````
Based on the provided sources, the `case()` construct in SQLAlchemy 2.0 no longer accepts a **list** of WHEN conditions. The list form emits a deprecation warning in SQLAlchemy 1.4 and is removed in 2.0. Instead, WHEN conditions must be passed as **positional arguments** (tuples).

**Old (deprecated) form — list of tuples:**
```python
case_clause = case(
    [(table.c.x == 5, "five"), (table.c.x == 7, "seven")],
    else_="neither five nor seven",
)
# list emits a deprecation warning [1][2]
```

**New (2.0) form — positional tuples:**
```python
case_clause = case(
    (table.c.x == 5, "five"), (table.c.x == 7, "seven"),
    else_="neither five nor seven"
)
# case conditions passed positionally [1][2]
```

The migration guide explains that this change aligns `case()` with SQLAlchemy's convention: **structural elements** (like WHEN clauses that form the statement structure) are passed **positionally**, while **data elements** (parameterized values) are passed as lists [2].
````

## g099 — `MappedAsDataclass` upgrade issue: `Column [...] has no Python-side or server-side default generator`

**Verified answer chunks:** c02072, c02074, c02075  
**Pages given to the model:** c01795, c00159, c01801, c02073, c02074  
**Judge's reason:** Passage [5] explains the changed meaning of `default` in `MappedAsDataclass`.

**Answer:**

````
Based on the provided sources, the error `Column [...] has no Python-side or server-side default generator` when using `MappedAsDataclass` in SQLAlchemy 2.0 likely stems from the changed meaning of the `default` parameter in `mapped_column` when dataclasses are enabled.

**Key changes in SQLAlchemy 2.0 with `MappedAsDataclass`:**

1. **`default` only accepts constant values** — When using `MappedAsDataclass`, the `default` parameter of `mapped_column` **must be a constant value** (e.g., a string, number, or `None`) and is applied to the object **immediately upon construction** (per PEP‑681 dataclass semantics). It is **not** allowed to be a callable. [5]

2. **Use `default_factory` for callables** — If you need a callable (e.g., a function or lambda) to generate a default value **at object construction time**, you must use `default_factory` instead of `default`. [5]

3. **`default` and `insert_default` are mutually exclusive** — With `MappedAsDataclass`, the value given to `default` is also propagated to the underlying `Column.default` (so it will be used in an INSERT if the attribute is not set). However, you **cannot** use `insert_default` at the same time as `default`. [5]

4. **Without `MappedAsDataclass`, `default` and `insert_default` are synonyms** — In classic (non‑dataclass) mappings, `default` and `insert_default` are interchangeable and can be callables; they only take effect when an INSERT is emitted, not at object construction. [4]

**Practical resolution for the error:**

- If you were previously passing a callable to `default` (e.g., `default=uuid.uuid4`), change it to `default_factory=uuid.uuid4`.
- If you need a **Python‑side default that only fires at INSERT time** (not at object construction), you cannot use `default` (because it applies at construction) and you cannot combine it with `insert_default`. Instead, consider using a **server‑side default** such as `server_default` (e.g., `server_default=func.gen_random_uuid()`) or an `Identity` column for auto‑incrementing primary keys. [1], [3]
- If the column is a primary key that should be generated by the database, use `Identity` (for PostgreSQL, Oracle, SQL Server, etc.) or a `Sequence` with `server_default=seq.next_value()` (PostgreSQL only). [1], [3]

**What the sources do not cover:**  
The exact error message `Column [...] has no Python-side or server-side default generator` is not explicitly mentioned in the provided excerpts. The answer above infers the cause from the documented behavior of `default`, `default_factory`, and `insert_default` with `MappedAsDataclass`. If the error persists after adjusting these parameters, further investigation into the specific column configuration (e.g., `nullable=False`, `autoincrement`, ORM‑level `init=False`) may be needed.
````

## g106 — `joinedload` polymorphic relationship: child-class columns are not loaded

**Verified answer chunks:** c00902, c00903  
**Pages given to the model:** c01347, c00881, c00983, c00903, c00967  
**Judge's reason:** Passage [4] shows that you must use `with_polymorphic` with `joinedload` to include subclass tables, but it does not explicitly state that `joinedload` alone only loads base‑class columns.

**Answer:**

````
Based on the provided sources, when using `joinedload` on a polymorphic relationship (inheritance hierarchy), child-class columns are not loaded by default because `joinedload` only loads the base class columns unless you explicitly include the subclass tables using `with_polymorphic`.

**Key points from the documentation:**

1. **Polymorphic loading requires explicit configuration** — Source [2] states: "When an attribute of a particular subclass is queried up front, we can use it in our query as something to filter on, and it also will be loaded when we get our objects back. If it's not queried up front, it gets loaded later when we first need to access it. Basic control of this behavior is provided using the `with_polymorphic` function..." [2]

2. **`with_polymorphic` must be used with `joinedload` for polymorphic relationships** — Source [4] explicitly addresses this: "When using `with_polymorphic` in conjunction with `joinedload`, the `with_polymorphic` object must be against an 'aliased' object, that is an instance of `Alias`..." It shows the pattern:
   ```python
   session.query(Company).options(
       joinedload(Company.employees.of_type(manager_and_engineer)).\
       subqueryload(manager_and_engineer.Engineer.computers)
   )
   ```
   Here `manager_and_engineer` is a `with_polymorphic` object (with `aliased=True` or `flat=True`), and `of_type()` targets the specific subtype. [4]

3. **`joinedload` creates anonymous aliases** — Source [1] and [5] explain that `joinedload` creates anonymously aliased joins that "do not affect the query results" and cannot be referenced directly. This is by design so that eager loading doesn't change the result set. [1, 5]

**Therefore, to load child-class columns in a polymorphic `joinedload`:**
- Create a `with_polymorphic` object (using `aliased=True` or `flat=True`) that includes the desired subclasses.
- Use `relationship.of_type(polymorphic_object)` as the target of `joinedload`.
- You can then chain further loaders (like `subqueryload`) on specific subclass attributes via the polymorphic object's namespace.

**What the sources do not cover:** The sources do not provide a complete minimal code example showing the exact `with_polymorphic` construction (e.g., `with_polymorphic(Employee, [Manager, Engineer], aliased=True)`) nor do they explain the behavior when using `selectinload`/`subqueryload` instead of `joinedload` for polymorphic collections. They also do not discuss SQLAlchemy 2.0 API changes (all sources are 1.4.52).
````
